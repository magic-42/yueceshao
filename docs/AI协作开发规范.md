# AI 协作开发规范（AI 写码 · AI 预审 · 人终审）

> 参考来源：Anthropic Claude Code 团队公开的 AI 编码工作流最佳实践，结合本团队实测（PR #6 首次完整走通"队员+AI 写码 → AI 预审 → 负责人终审合并"）整理。
> 与其他文档的分工：`README.md`＝红线与编码规范；`docs/协作规范.md`＝git 流程；`开发手册`＝模块任务与验收标准；**本规范＝人与 AI 协作写代码的质量流程**。

## 1 核心循环

```text
[计划先行] AI先出设计要点 → 负责人批准计划
      ↓
[TDD实现] 关键路径先写测试看它红 → 再实现看它绿
      ↓
[自查+PR] 按PR模板发PR（做了什么/怎么测/红线自查/AI参与声明）
      ↓
[AI预审] 独立上下文的AI实例按清单审PR，意见写入PR评论
      ↓
[人终审] 负责人看AI意见+亲自看diff → squash合并 → 删分支
      ↓
[CI兜底] GitHub Actions 自动跑 pytest，红=不算完成
```

**铁律：永不盲并。** AI 写的代码"看起来对"和"对"是两回事——无论谁写的 PR（人/ AI/ 人+AI），未经审查不得合并。

> 2026-11-06 修订：「AI 预审」与「人终审」两步**可一并委托**给独立会话的"审核与合入代理"，但仅限 §8 通道 A 的小改动；通道 B 一律回到负责人手上（负责人可逐次明示授权独立会话代审，须留痕，见 §8.2）。步骤与授权边界见 §8。

## 2 计划先行（超过 200 行的 PR）

Anthropic 团队最重要的经验：**改代码之前先改计划**。计划批错成本是分钟级，代码审错成本是小时级。

- 触发条件：预计 diff >200 行，或引入新数据结构/新依赖/新接口；
- 计划内容（写在 issue 或 PR 草稿里，五行以内）：要动哪些文件、核心数据结构、对外接口、测试方案；
- 负责人回复"计划 OK"后才开写。开发手册§3 的 PR 表格已预先固定了各 PR 的骨架，视同计划已批。

## 3 TDD：四个关键路径必须"先红后绿"

以下四类是引用零容错的地基，**必须先写测试、亲眼看它失败、再实现、看它变绿**（其余 PR 至少附带测试即可）：

| 关键路径 | 对应模块 | 为什么不能错 |
|---|---|---|
| 分块对齐（条款号↔chunk一一对应） | rag/chunker | 错位=引用错误率指标崩塌 |
| 时效硬过滤 | rag/retriever | 漏过滤=误引已失效条款 |
| 引用校验器 | gen/validator | 它是幻觉的最后防线 |
| 规则命中 | rules/engine | 误报/漏报直接进报告②段 |

## 4 PR 描述模板（`.github/PULL_REQUEST_TEMPLATE.md` 已配置）

发 PR 时 GitHub 会自动带出六栏模板，**全部填写**再请求审查：

1. **做了什么**（对应开发手册哪个 PR 编号）；
2. **为什么这样做**（关键取舍一句话）；
3. **怎么测的**（pytest 结果、本地验收输出）；
4. **红线自查**（六条红线逐条 ✅/不适用）；
5. **输出样例**（命令行截图或文本，demo 类 PR 必附页面截图）；
6. **AI 参与声明**（谁写的：人 / AI工具名 / 人+AI）。

## 5 AI 预审 + 人终审（双保险）

Anthropic 的实测结论：**换一个全新上下文的 AI 实例审 PR，能发现疲劳的人眼和写码的 AI 自己都漏掉的问题**。我们的落地：

- **AI 预审**：负责人把 PR 交给一个独立 AI 会话（非写码的那个），按固定清单审查并把结论写成 PR 评论——清单=六条红线＋编码规范＋测试覆盖＋边界条件＋与开发手册验收标准逐条比对；
- **人终审**：负责人（杨宇翔）最后亲自过 Files changed，重点看 AI 意见中标记的风险点；AI 意见是参考不是免检通行证；
- AI 预审者**默认不合并**——合并权在负责人，与仓库保护机制一致；唯一例外是 §8「分级委托合并」：负责人可把"审＋合"一并委托给独立会话的代理，且只在通道 A 的六项条件全部成立时生效；通道 B 仍须负责人终审（或经负责人逐次明示授权的独立会话代审，须在 PR 与台账留痕，见 §8.2）。

## 6 CI 兜底（`.github/workflows/ci.yml` 已配置）

- 每个 PR 自动：装依赖（若存在 requirements.txt）→ 跑 pytest（若存在测试）；
- **CI 红=不许请求审查**，先把测试修绿；
- 这条把开发手册"PR 必附 pytest"从自觉变成机制。

## 7 会话纪律（AI 使用的五条习惯）

1. **独立工作副本（铁律，2026-11-02 实测事故引入）**：每个开发者、每个 AI 会话必须使用**独立的克隆或 git worktree**，严禁两个会话共享同一个目录切分支——实测中两个会话在共享副本上并发操作，导致一方的提交落到另一方分支上、另一方的工作树被切走。隔离方式任选其一：
   - 各自 `git clone` 到自己的目录（推荐队友与 harness 会话用这个）；
   - 同一克隆内用 `git worktree add ../目录名 分支名` 给每个会话开独立工作树（本地多会话推荐）。
2. **一个任务一个会话**：上下文不跨任务复用——写码会话里积累的假设会把下一个任务带偏；任务切换就开新会话（对应 Claude Code 的 /clear 习惯）；
3. **检查点交付**：长任务（如一次开发两个 PR）在中途检查点停下等指令，不一口气跑完；
4. **AI 参与透明化**：AI 编写/参与编写的 PR 打 `ai-authored` 标签——不伪装纯手写，也便于事后统计 AI 协作的实际质量（答辩时是加分的工程化素材）。
5. **预审前置（2026-11-06 增）**：写完 PR 只交预审、**不合入自己写的 PR**；并行多会话下同样适用。细则与事故依据见 §8.4。

## 8 合并授权分级（2026-11-06 修订：原「AI 自动合并小 PR：不采用」→「分级委托合并」）

原条款「AI 自动合并小 PR：不采用」的理由是**合并权集中是协作基石**。该理由在 2026-11 的实践中被部分修订而非废弃：合并权仍归负责人，但**负责人可将"审＋合"两件事一并委托给一名独立会话的"审核与合入代理"**，前提是下文的护栏全部成立。委托是**分级**的——多数小改动走通道 A，凡触及引用零容错面的一律走通道 B 回到负责人手上（逐次授权代审的例外见 §8.2）。

### 8.1 角色与前提

- **审核与合入代理**＝一个**独立会话**（独立克隆／独立上下文），负责"AI 预审＋终审判断＋执行合并"三项。它把 §5 的"AI 预审＋人终审"两步合一。
- **写码与合入必须不同会话**：代理**不得**合并自己会话写出的 PR；需要交叉时，在 PR 里明确标注写码会话身份与代理会话身份。
- **代理不新增权限**：分支保护、必需检查、无人能直接 push main 等机制全部不变；代理执行合并用的仍是 owner 账号，**授权来源始终是负责人的明示委托**。

### 8.2 通道判定（每个 PR 先定级，再走对应通道）

**通道 A：代理可直接合入**（须**同时**满足全部条件）

| # | 条件 |
|---|---|
| 1 | 类别＝chore／docs／测试增强／风格与 lint／依赖小版本／README 类文档同步 |
| 2 | CI 双必需检查（`test`＋`lint`）全绿；CodeRabbit 无阻断级意见（`COMMENTED` 可，`CHANGES_REQUESTED` 不可） |
| 3 | 代理**独立实测**通过：独立副本检出分支、pytest 全绿、ruff 零告警（本 PR 触碰文件） |
| 4 | diff ≤ 200 行 |
| 5 | 不触碰：`gen/` 的防线与提示词、`rules/` 的词典与 schema、评测口径与指标定义、demo 数据（`docs/js/data.js`）、标注表数据 |
| 6 | PR 描述六栏齐全（§4）且与 diff 一致 |

**通道 B：必须负责人终审**（未获逐次授权时代理只做预审评论）——任一命中即升级

- 新功能模块或新外部依赖；
- `gen/` 防线、提示词、`rules/` 词典、schema 的任何变更；
- 评测口径、指标定义、阈值变更；
- 触碰六条红线相关面；
- diff > 200 行或跨 ≥3 个模块；
- 标注表／负对照／数据仓口径变更；
- 与其他未合并 PR 存在堆叠或冲突路径；
- **代理拿不准的（拿不准即升级，不猜）**。

升级格式：在 PR 评论写「**【需负责人终审】**」＋完整审查意见＋建议方案，并向负责人汇报一句。

**通道 B 的终审权归负责人。** 唯一例外是**逐次明示授权代审**（2026-11-06 负责人拍板）：

- 必须**逐 PR** 明示（例：负责人说"PR #47 由你终审后合并"），**一次授权只覆盖它点名的那个 PR 的这一轮**，不可复用到后续 PR 或同一 PR 的后续轮次；
- 代审会话必须是**独立会话**（写码会话不得代审自己的 PR，见 §8.1）；
- **必须留痕**：在 PR 评论写明「负责人授权代审」＋授权原话与日期，并在 **`docs/合并台账.md`**（仓内正式台账）对应行注明授权出处；
- 未获逐次授权 → 代理只发预审评论，**合入动作等负责人本人执行**。

### 8.3 护栏（缺一视为违规）

1. **合并台账（仓内）**：每次合入向 **`docs/合并台账.md`** 追加一行——日期／PR 号／通道判定／核验要点／合并 commit sha。该文件在代码仓内（2026-11-06 由团队工作区迁入），随 PR 一起被审查、任何人 clone 可见、`git log` 天然留痕；**允许滞后一次合入**（PR X 的台账行可随下一个 PR 补记），逾期=漏记，**漏记视同违规**。依据"负责人会话指示／授权代审"合入的，必须注明授权原话与日期。
2. **合并后三验**：① PR `state=MERGED`（回查，防静默失败）② 远端 main head 前进 ③ main 上 CI 新跑一轮绿；违反严格保护（`BEHIND`）时先同步再合。
3. **码上不留疑**：审核清单＝六条红线逐条 ✅/❌＋与开发手册验收标准逐条比对＋"PR 自述与实际 diff 是否一致"（历史高发区）＋CodeRabbit 意见逐条分类（已落实／未落实／不认同并给理由）。
4. **汇报节奏**：每合并满 5 个 PR 或每完成一轮审核，向负责人发合并清单汇总。

### 8.4 预审前置（2026-11-06 增，因实测事故引入；负责人同日拍板）

**任何 PR 在合入 main 之前必须先经过一次独立预审；写码会话不得合并自己会话写出的 PR。** 这条对人与 AI、对单会话与并行多会话一律适用，**顺序不可颠倒**。

**事故依据**：2026-11-06 PR **#45**（LangGraph 图级条件边＋真实 LLM 蕴含复核节点，330 行、改动②段生成链路＝通道 B）由 owner 账号直接合入，**PR 内零 AI 预审评论、合并前未进合并台账**。事后补验 main 未受损（461 passed／ruff 0），但风险是实打实的：通道 B 的 PR 就这样跳过了「六条红线＋独立实测＋自述与 diff 一致性」三道检查。

| 情形 | 要求 |
|---|---|
| 单会话写码 | 发 PR → 交代理预审（通道 A 预审通过可合；通道 B 按 §8.2 由负责人终审，或经**逐次明示授权**的独立会话代审）→ 才可合入 |
| **并行多会话同时写码** | 每个 PR 独立走上面这条；**任何写码会话都不得合入自己的 PR**，也不得合入自己参与过口径讨论的 PR |
| 写码会话发现别人的 PR 有阻断项 | 只能评论指出，**不得代改＋代合**（改了就换身份，须另起独立会话终审） |
| 已合入但未经预审的 PR | 代理**只能事后核验**（全仓测试＋红线扫描）并在台账标注「未经预审合入」；**不得事后补绿灯伪装合规** |

**给写码会话的收尾话术**（并行会话尤其照做）：修完 → 同步 main → CI 双绿 → 在 PR 留一句「已修 X，CI 双绿，请终审」→ **停下等终审**，不要执行 `gh pr merge`。

### 8.5 仍然不采用（防止过度工程）

| 做法 | 不采用理由 |
|---|---|
| CI 容器里跑自主 agent（跳权限自动修 PR） | 测试量还少、信任未建立；等测试套件成型后再议 |
| Slack/GitHub 深度通知集成 | 微信＋GitHub Watch 已够用 |
| 「无人在环」的自动合并（无授权矩阵、无台账、无升级机制） | 合并权集中仍是基石；本节的委托是**有边界、有留痕、可抽查**的委托，不是自动化 |

例外（2026-11-03 增）：**允许接入只读型 AI 审查 bot（如 CodeRabbit）作为第一道预审参考**——它只发评论、无阻塞权、不自动改码、不参与合并；项目红线与验收标准的把关仍由「独立上下文 AI 预审＋人终审」承担。

### 8.6 数据仓 push 专项（2026-11-07 增；永远通道 B）

数据仓（kohl7614/yueceshao-data，本地工作树 `04_政策语料/`）的 push **不走 §8.2 的通道 A/B PR 判定**，而是一律按**通道 B**处理：

- **只有负责人本人，或负责人明示授权的独立会话**可执行 `git push`；写码会话不得 push 数据仓（无论改动大小）；
- 数据仓改动（`registry.json` 主台账、案例标注表、条款归并 json、清洗文本、页面快照等）**无小改动例外**——哪怕一行注释，也不走代理直合；
- 理由：数据仓是共享敏感数据（733 篇语料＋评测出题集＋唯一主台账），误 push 影响面大、历史不可逆，门槛应高于代码仓；
- 留痕：数据仓每次 push 的 commit message 写清「谁授权、改了什么」，并在 `docs/合并台账.md` 记一行（含数据仓 commit sha）；
- 代码仓的通道 A/B 判定与本节互不影响（代码仓 PR 照旧走 §8.2）。
