# 协作规范（git 工作流，全队必读）

> 本文件写给**人和 AI 助手**：队友的 agent 开工前必须先读本文件与仓库 `README.md`。
> 协作模型一句话（2026-11-02 更新）：**队友已被邀请为仓库协作者——直接在仓库里开功能分支开发 → 发 Pull Request → owner 审阅合并**。`main` 有分支保护（要求 PR、含管理员），写权限只能推功能分支、动不了 main，安全性与原 fork 流程完全等价。**不再推荐 fork 流程**（fork PR 的 CI 需逐个手动批准，且 fork 同步麻烦）；外部无权限贡献者仍可走 fork。

## 一、首次建仓（✅ 已完成，2026-10-30；仓库地址 https://github.com/kohl7614/yueceshao ，队友请从第二节开始读）

仓库已初始化并推送，main 分支保护已开启（要求 PR、含管理员、禁止 force push 与删除）。以下命令仅作存档：

```bash
cd 05_项目代码/粤策哨系统        # 本目录即仓库根
git init -b main
git add . && git commit -m "chore: 初始化仓库（README/协作规范/.gitignore）"
git remote add origin https://github.com/kohl7614/yueceshao.git
git push -u origin main
```

分支保护规则（Settings → Branches）：分支名 `main`，勾选 *Require a pull request before merging*＋*Include administrators*——任何人（包括 owner 自己）都无法直接 push main，改动必须走 PR，"采用权在 owner"由此从约定变成机制。

## 二、队友环境准备（每人一次性，10 分钟）

1. 注册 GitHub 账号，装 git；接受仓库协作者邀请（GitHub 右上角铃铛）；
2. 直接克隆仓库（就这一个，无需 fork）：

```bash
git clone https://github.com/kohl7614/yueceshao.git
cd yueceshao
```

## 三、日常开发六步（每次任务都照这个来）

```bash
# 1. 先同步，保证基于最新代码开发
git switch main && git pull

# 2. 开任务分支（分支命名见下表）
git switch -c feat/rag-chunking

# 3~4. 写代码、提交（commit 规范见下表；小步提交，别一次巨量）
git add <相关文件>
git commit -m "feat: 条款结构感知分块器"

# 5. 推到仓库的功能分支
git push -u origin feat/rag-chunking

# 6. 到 GitHub 网页（或 gh pr create --fill），从你的分支向 main 发 Pull Request
```

## 四、命名与提交规范

| 项 | 规范 | 示例 |
|---|---|---|
| 分支名 | `feat/模块-简述`、`fix/...`、`docs/...`、`exp/消融编号` | `feat/rules-engine`、`exp/ablation-3` |
| commit | `类型: 一句话说明`（feat / fix / docs / test / chore） | `fix: 时效过滤误判已截止指南` |
| PR 标题 | 同 commit 规范 | `feat: 负面清单规则引擎首版` |
| PR 描述 | 三行：**改了什么 / 为什么 / 怎么自测的**（AI 参与的注明"AI 参与完成＋人工已检查〈范围〉"） | — |

## 五、审阅与合并规则

- **任何 PR 合入前必须先经独立预审**，写码者不得合并自己写的 PR（细则见 [AI协作开发规范](AI协作开发规范.md) §8）；
- 合并权归 owner；通道 A 的小改动可委托独立会话的「审核与合入代理」直接合入，**通道 B 仍须 owner 终审**（可逐次明示授权代审，须在 PR 与 `docs/合并台账.md` 留痕）；
- **未经上述审查与授权，任何改动不进 main**；
- PR 保持小而聚焦：一个 PR 只做一件事，不改无关文件；
- owner 有权要求修改；队友在原分支继续提交并 push，PR 自动更新；
- 冲突处理：`git fetch upstream && git merge upstream/main` 到自己分支解决后 push。

## 六、禁止事项（红线）

1. **不直接 push 到 main**（分支保护已开，试也会被拒）；
2. 不 force push 共享分支；自己的任务分支可以 rebase 后 force push；
3. **不提交任何密钥 / API key**：`.env`、真实 `config.json` 已被 `.gitignore` 挡住，只提交 `.example` 文件；
4. 不提交政策语料原文、评测标注表等数据文件（它们在团队工作区，不在代码仓库）；
5. 不提交大文件（模型权重、PDF 等）；
6. 不改与任务无关的文件，不顺手重构。

## 七、AI 助手协作条款（队友的 agent 必读）

1. 开工前先读仓库 `README.md`（项目背景、架构、红线、编码规范）与本文件；
2. 在任务分支上工作，完成即发 PR，**绝不尝试合并自己的 PR 或改动 main**；
3. 严格遵守 README 的"开发红线"（不编造文号 / 不手打文号 / 姿态禁语 / 审计公告隔离等）；
4. 需要政策文本样例时向人索取，不凭记忆生成文号；
5. PR 描述注明 AI 参与情况和人工检查范围；
6. 拿不准就停下来问人。

## 八、给队友的一句话启动模板（发给你的 agent）

> 读仓库根目录的 README.md 和 docs/协作规范.md，然后完成任务：〈在此写任务，如"实现 rag/ 下的条款结构感知分块器，输入清洗文本，输出带元数据的条款 chunk JSON"〉。在分支 `feat/〈模块〉` 上开发，完成后告诉我如何提交 PR；不要改动 main，不要提交密钥和数据文件。
